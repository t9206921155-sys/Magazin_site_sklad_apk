## Цель

Поддержать несколько складов в одной базе: у товара появляется привязка к
складу, остатки считаются по каждому складу отдельно, сотрудник видит только
свои склады.

## Контекст

Сейчас склад один и неявный: остаток лежит прямо в `products.stock`.
Роли уже есть — `admin` / `worker` в таблице `wh_users`
(`store.py`, метод `wh_add_user`, проверка в `api.py` → `wh_user_from_headers`).

Ключевые места:

- `store.py` — `wh_users()`, `wh_add_user()`, `_apply_product_fields()`,
  `update_stock_by_code()`, `_change_stock()`;
- `api.py` — блок `/api/warehouse/*` (примерно строки 1880–2400);
- `warehouse/app.js` — список товаров `loadList()`, форма товара, настройки;
- миграции — `store.py`, метод `_migrate_columns()`.

## Отчёт

**Выполнено.**

### Схема БД

Три новые таблицы в `SCHEMA` (`store.py`):

| Таблица | Назначение |
|---|---|
| `warehouses` | `id`, `name`, `address`, `is_active`, `created_at` |
| `wh_stock` | `product_id` + `warehouse_id` → `qty` (PK по паре) |
| `wh_user_access` | какой пользователь к каким складам допущен |

`products.stock` **намеренно не тронут** — остаётся суммарным остатком для
витрины, бота и 1С. Разбивка живёт в `wh_stock`, суммарное поле
пересчитывается методом `_sync_total_stock()` при любом изменении.

### Миграция

`_migrate_warehouses()` — идемпотентная: создаёт склад «Основной», переносит
в него текущие остатки (`stock > 0`), выдаёт админам доступ ко всем складам.

Проверено на боевой базе: 8 товаров, 81 единица — **0 расхождений**
между `products.stock` и `wh_stock`.

### API

- `GET/POST/PUT/DELETE /api/warehouse/warehouses` — управление (создание,
  изменение и удаление только для роли `admin`)
- `GET/POST /api/warehouse/products/{pid}/stock` — разбивка и установка остатка
- `POST /api/warehouse/transfer` — атомарное перемещение
- `GET/PUT /api/warehouse/users/{uid}/warehouses` — доступы сотрудника
- `POST /api/warehouse/scan` — принимает `warehouse_id`, операции
  `receive`/`sell`/`inventory` меняют остаток конкретного склада

Хелпер `_wh_access_or_403()` централизует проверку доступа.

### Найденный баг (поймали тесты)

Первый прогон дал **10 падений**: новый товар не попадал в `wh_stock` —
миграция обрабатывала только существующие записи, а `add_product()` о
мультискладе не знал. Товар создавался с остатком, но разбивка была пустой,
и перемещение падало с «на складе 0».

Исправлено в `store.add_product()` — стартовый остаток кладётся на склад по
умолчанию (или на указанный в `warehouse_id`). Правка сделана в `store.py`,
а не в эндпоинте, поэтому покрывает и импорт, и 1С, и админку.

Дополнительно `stock_breakdown()` получил фолбэк: если записей в `wh_stock`
нет (старые данные, импорт в обход), показывает остаток на складе по
умолчанию, чтобы товар не «пропал» из интерфейса.
