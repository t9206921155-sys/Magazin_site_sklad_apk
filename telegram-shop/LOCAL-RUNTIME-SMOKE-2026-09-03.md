## Найденный и исправленный баг: удаление товара со склада

**Симптом.** Кладовщик не мог удалить товар из интерфейса склада.

**Причина — две несогласованности:**

1. Эндпоинта `DELETE /api/warehouse/products/{pid}` **не существовало** — прямой
   вызов возвращал **405 Method Not Allowed**. Были только `archive` и `bulk`.
2. UI склада (`warehouse/app.js`, функция `delProduct`) ходил в
   `DELETE /admin/api/products/{pid}` — а этот маршрут защищён `require_admin()`
   и требует **админ-токен магазина**. Кладовщик со своим `X-WH-Token`
   получал **403 «Нет доступа»**.

Воспроизведено до правки: создание товара -> `DELETE /admin/api/products/{id}`
с `X-WH-Token` -> `403 {"detail":"Нет доступа"}`.

**Исправление:**

- `api.py`: добавлен эндпоинт `DELETE /api/warehouse/products/{pid}` рядом с
  `archive`. Требует роль `admin` склада, проверяет существование товара,
  пишет запись в журнал действий через `store.wh_log_add`.
- `warehouse/app.js`: `delProduct()` теперь вызывает
  `/api/warehouse/products/{id}` вместо `/admin/api/products/{id}`.
  Ветка `isDirectMode()` (Supabase direct) не тронута.

**Проверка после правки:**

| Сценарий | Ожидание | Факт |
|---|---|---|
| `DELETE` существующего товара | 200 | **200** `{"ok":true,"id":11}` |
| `GET` удалённого товара | 404 | **404** |
| `DELETE` несуществующего id | 404 | **404** |
| `DELETE` без токена | 403 | **403** |
| Запись в журнале | есть | **есть** — «удалил товар Del тест 2 (id 11)» |

Синтаксис проверен: `api.py` — `ast.parse` OK, `warehouse/app.js` — `node --check` OK.

## 2. Этап 3: HID-приём Bluetooth/ТСД доведён до рабочего

Было помечено в коде и в меню как «Заглушка (stub)». Разбор показал, что
проблема не в полноте, а в **неверной логике парсера** — четыре дефекта:

1. **Мёртвая ветка.** `if (delta < 150 && delta > 5) {...} else {...}` — обе ветки
   выполняли идентичный код, то есть проверка скорости ввода ни на что не влияла
   и ручной ввод человека тоже копился в буфер сканера.
2. **Склейка кодов.** Если сканер не слал Enter, буфер никогда не очищался, и
   следующий скан дописывался к предыдущему (`1111...` + `2222...`).
3. **Нет поддержки сканеров без Enter-суффикса** — такой код не отправлялся вообще.
4. **Двойное срабатывание** при дребезге: повторный скан того же кода уходил дважды
   (в режиме `sell` это списало бы товар два раза).

**Реализовано:**

- отсечка ручного ввода по межсимвольному интервалу (`FAST_MS = 35 мс`);
- сброс буфера при паузе — коды больше не склеиваются;
- поддержка сканеров **без** Enter: отправка по тишине (`IDLE_FLUSH = 120 мс`),
  переключатель «Сканер шлёт Enter в конце» в интерфейсе;
- дедупликация повторного кода в окне `DEDUP_MS = 700 мс`;
- отсечка шума короче 4 символов;
- живой лог принятых кодов, кнопка вкл/выкл приёма, показ текущего режима
  (Поиск / Приёмка / Продажа / Инвентаризация);
- из меню и комментариев убрано слово «заглушка».

**Тесты логики парсера** (`node`, 8 проверок) — все проходят:

| Сценарий | Итог |
|---|---|
| Сканер с Enter-суффиксом | ✅ |
| Два скана подряд не склеиваются *(был баг)* | ✅ |
| Скан без Enter не оставляет мусор *(был баг)* | ✅ |
| Медленный ручной ввод не считается сканом *(был баг)* | ✅ |
| Дедупликация повторного скана *(был баг)* | ✅ |
| Повтор после паузы принимается снова | ✅ |
| Сканер без Enter — отправка по паузе | ✅ |
| Короткий шум отброшен | ✅ |
